## 一、项目定位与总体架构

这是一个**行为克隆（Behavior Cloning / 模仿学习）**项目：先用人工操作录制"画面 → 按键"的配对数据，训练一个 5 分类图像分类器，再让模型实时看游戏画面、自动按键玩游戏。

完整的四段式流水线：

```
① 采集  caiji.py / shuju.py     人工按键 → ADB 截图 → 按类别落盘 W/A/S/D/N
              ↓
② 清洗  sj/改名.py  删除翻转图片.py  name.py  tj.py
              ↓
③ 训练  trian.py                EfficientNet-B0 迁移学习 → best_model.pth
              ↓
④ 部署  auto_wasd.py            实时截屏 → 模型推理 → pynput 模拟按键
```

| 环节 | 文件 | 说明 |
|---|---|---|
| 采集（基础版） | `caiji.py` | 按键触发截图，X 键删除最近 10 张，Esc 退出 |
| 采集（增强版） | `shuju.py` | 增加"空闲 1.5s 自动补 N"与"方向键后自动删除过近的 N" |
| 重命名 | `sj/改名.py`、`name.py` | 统一"前缀_编号"命名 |
| 清洗 | `sj/删除翻转图片.py` | 删除文件名含 `flip` 的图片 |
| 统计 | `tj.py` | 统计各类别图片数量 |
| 训练 | `trian.py` | EfficientNet-B0，分层 7:1.5:1.5 |
| 部署 | `auto_wasd.py` | FP16 推理 + 类别阈值 + 防抖 + Grad-CAM |
| 辅助 | `biaoti.py` | 列出窗口标题（用于确认模拟器窗口名） |

## 二、数据集现状（实测）

### 2.1 规模与分布

| 数据集 | 总数 | A | D | N | S | W | 体积 |
|---|---|---|---|---|---|---|---|
| `paoku\sj`（新，训练用） | **3181** | 626 | 647 | 635 | 637 | 636 | 1.03 GB |
| `paoku\(A/D/N/S/W)`（旧） | 491 | 25 | 19 | 33 | 270 | 144 | — |

- 图片规格统一：**720×880，RGBA**，全部来自裁剪框 `(0, 200, 720, 880)`。
- **无完全重复**：3181 张全部 MD5 去重后无重复组；新旧数据集之间也**零重叠**。
- 新数据集类别**高度均衡**（各类 626–647），旧的严重偏斜（S 类占 55%，A 类仅 25 张）——说明新数据集是有意重新平衡采集的。

### 2.2 类别语义

| 类别 | 按键 | 游戏动作 |
|---|---|---|
| W | w | 上滑（跳跃） |
| A | a | 左移换道 |
| S | s | 下滑（翻滚） |
| D | d | 右移换道 |
| N | 无 | 不操作（直行） |

### 2.3 数据质量问题（已定位）

1. **错标文件**：`sj\D\` 中混入 5 个以 A 命名的文件 —— `A_013.png`、`A_045.png`、`A_112.png`、`A_625.png`、`A_634.png`（`sj\A` 中并不存在同名文件）。`ImageFolder` 按父目录给标签，这 5 张会被当作 **D 类** 参与训练，属真实错标（占比 0.16%，影响小但应清理）。
2. **N 类冗余度最高**：类内近邻距离 ≤2.0 的"双胞胎帧"比例 —— N 类 **13%**、W 类 11%、A/D 各 5%、S 类仅 1%。这与 `shuju.py` 每 1.5 秒空闲自动补一张 N 的机制直接相关。
3. **编号不连续**：`x` 键删除文件后不回收计数器，因此存在 `w_0116 → w_0121`、`a_0140 → a_0142` 之类的跳号（无害，但削弱可追溯性）。
4. **文案与实际不符**：`shuju.py` 打印"删除最近 4 张"，而实际 `deque(maxlen=10)`。
5. **S 类辨识度存疑**：翻滚动作与直行在单帧下差异很小（类内双胞胎比例最低也从侧面说明 S 帧变化最剧烈，但 S 与 N 的混淆未被评估——训练脚本未输出混淆矩阵）。

## 三、模型与训练（`trian.py`）

### 3.1 配置

```
模型        EfficientNet-B0（ImageNet 预训练）+ Dropout(0.3) + Linear(1280 → 5)
输入        224×224
训练增强    RandomResizedCrop(224, scale=0.8~1.0) + ColorJitter(0.2/0.2/0.2/hue 0.1)
            —— 明确排除了翻转与旋转（方向分类必须排除翻转，这一点做对了）
评估变换    Resize(256) + CenterCrop(224) + ImageNet 归一化
优化        AdamW(lr=1e-3, weight_decay=1e-3)
调度        ReduceLROnPlateau(mode=min, factor=0.5, patience=5)
早停        EarlyStopping(val_loss, patience=12, delta=0)
批次/轮数   batch=32, max 60 epochs
划分        分层 70/15/15，seed=42 → 2226 / 477 / 478
```

### 3.2 训练结果（`training_curves.png`）

- 实际训练 **约 32 个 epoch**。
- 训练准确率 → **100%**；验证准确率 ≈ **97–98%**；验证损失最低约 **0.06**（约 epoch 17）后回升到 **0.09**。
- 训练损失趋近 0 而验证损失上行 —— **典型过拟合**。早停监控的是 val_loss，配合 patience=12 允许了较长的过拟合区间。

### 3.3 权重文件混乱（需整理）

| 文件 | 时间 | 体量 | 内容 |
|---|---|---|---|
| `001.pth` | 8/8 15:41 | 16.4 MB | 裸 `state_dict`，**部署脚本实际加载的就是它** |
| `best_model.pth` | 8/5 22:08 | 16.4 MB | 裸 `state_dict` |
| `best_model03.pth` | 8/7 23:28 | 16.4 MB | 裸 `state_dict`（与 training_curves.png 时间吻合） |

四个文件 MD5 互不相同。`efficientnet_b0_best.pth` 的优化器步数为 253、epoch 22，按 32 批量推算约对应 ~11 步/轮，与**旧小数据集（491 张）**的规模吻合 —— 它应是早期一轮训练的产物。

另外：`auto_wasd.py` 会尝试读取 `class_mapping.pth`，但该文件**全盘不存在**，`trian.py` 也从未生成它。目前靠 `ImageFolder` 的字母序（A,D,N,S,W）与硬编码 `CLASS_NAMES` 恰好一致而正常工作 —— **这是一个静默隐患**：一旦增删类别或改用其他数据集，标签会无声错位。

## 四、部署推理（`auto_wasd.py`）

### 4.1 流程

```
[截图线程]  adb exec-out screencap -p → 裁剪 (0,100,720,900) → Queue(maxsize=1)
      ↓
[控制循环]  Resize(256) + CenterCrop(224) + 归一化
      → EfficientNet-B0 (FP16) → softmax
      → 类别阈值判定（A 0.97 / D 0.97 / N 0.75 / S 0.90 / W 0.90）
      → N 直接跳过；同类别 0.5s 防抖
      → pynput 按下 0.01s
      ↓
[可视化]   Grad-CAM 热力图窗口 + 类别概率排序窗口
```

### 4.2 设计上的亮点

- 每个类别单独设阈值（换道类要求 0.97 高置信，避免误换道），比单一阈值更合理。
- 防抖机制（同一动作 0.5s 内不重复触发）。
- FP16 推理 + `cudnn.benchmark`，充分利用 4060。
- 权重加载有容错回退（`_safe_load_model`），会处理完整 checkpoint 与旧序列化格式。
- 内置 Grad-CAM 注意力可视化，便于调试"模型到底在看哪里"。
- N 类不动作 —— 逻辑正确。

## 五、问题清单（按严重程度排序）

### 🔴 P0-1　标签时序可能与画面错位（最值得验证的一点）

采集流程是"**按键事件 → 立刻 ADB 截图**"，而 `adb exec-out screencap -p` 本身有 100–300 ms 级延迟，此时角色**已经开始位移**。也就是说保存的画面很可能是"动作已发生"的画面，而不是"决策前"的画面。

我用类别均值图像做了验证：

| 指标 | 结果 | 含义 |
|---|---|---|
| `\|A − D\|` 差异能量分布 | 顶部 8.80 / 中部 13.35 / **底部 19.04** | 类别差异**集中在画面下方（角色所在位置）**，而不是上方的障碍物区 |
| `\|A − N\|` 最热列 | 67/180（中心 90 的左侧） | A 类画面中角色/主体偏左 |
| `\|D − N\|` 最热列 | 163/180（中心 90 的右侧） | D 类画面中角色/主体偏右 |

如果是正确的"动作前"标注，A 与 D 的差异本应主要体现在**前方障碍的布局**（画面上部），而角色都还在中线。实测恰好相反。

**后果**：模型可能学到捷径特征"角色已经偏左 → 预测 A"，离线准确率因此虚高；而在真正闭环时，模型看到的多是"角色居中、等待决策"的帧，分布不匹配，实际表现会明显低于 98%。

**验证方法（建议优先做）**：
1. 用 `scrcpy --record` 以 60 fps 录制一段人工操作，同时在按键时打时间戳；对比"按键前 1–2 帧"与"按键后帧"哪一个才是真正的输入。
2. 或修改采集脚本，记录 `按下时刻` 与 `截图返回时刻` 两个时间戳，直接量化延迟。
3. 若确认错位，取**按键前 100–200 ms 的那一帧**作为输入重训。

### 🔴 P0-2　训练与推理的裁剪区域不一致

| 阶段 | 裁剪框 | 实际区间（y） |
|---|---|---|
| 采集（`caiji.py` / `shuju.py`） | `(0, 200, 720, 880)` | 200 → 1080 |
| 推理（`auto_wasd.py`） | `(0, 100, 720, 900)` | 100 → 1000 |

经 `Resize(256)+CenterCrop(224)` 后，模型实际"看到"的纵向区间约为：训练 ≈ y 321–937，推理 ≈ y 235–865，**大约错位 86 像素**。同一画面在训练与推理时呈现内容不同，属于典型的训练/部署分布漂移。

**修复**：把推理端改回 `(0, 200, 720, 880)`，或（若确实想多看上方）用新裁剪框重新采集数据。

---

### 🔴 P0-3　随机划分造成的数据泄漏（已量化）

`trian.py` 用 `train_test_split(..., random_state=42)` **随机**划分 3181 张高度时序相关的游戏帧。我复现了同一划分并测量：

| 指标 | 结果 |
|---|---|
| val/test 帧到**训练集最近邻**距离（32×32 灰度 L2）中位数 | **3.68 / 3.78** |
| 同类**随机配对**距离中位数（基线） | 7.06 |
| → 即 val/test 帧离训练集只有"随机同类对"的 **52%** 距离 | |
| 最近邻距离 ≤ 2.0 的比例 | **5.8%** |
| ≤ 3.0 的比例 | **24.1%** |
| ≤ 3.5 的比例 | **41.0%** |
| **纯像素 1-NN 基线**（32×32 灰度，无任何训练）在同一划分上的准确率 | val **73.2%** / test **76.4%** |

结论有三层：
1. 一个**零参数的最近邻分类器**就能拿到 ~76%，说明 98% 这个数字里有相当一部分来自"相邻帧几乎一样"的记忆效应，**真实泛化能力被高估**。
2. 每张图与其训练集最近邻的距离中位数只有随机同类对的一半，说明数据集内部**冗余度高、有效独立样本远少于 3181**。
3. 以 τ=2.0 做近重复聚类，3181 张只坍缩成 3026 组（7.4% 的帧存在近似双胞胎），冗余并非极端，但 **τ 放宽到 3.0 时约有四分之一的测试帧能在训练集里找到"很像"的邻居**。

**修复**：改用**按连续片段/对局分组**的划分（`GroupKFold`），或按采集时间分块切分（前 70% 时间训练、后 30% 测试），并重新报告指标。若指标明显下滑，那才是模型真实水平的估计。

### 🟠 P1-1　单帧分类的方法学上限

游戏动作是否恰当，取决于**速度、障碍距离和时机**（"前方 0.3 秒会撞上，必须现在换道"），而输入只有一帧静态画面，模型无法表达时序。这是纯单帧行为克隆的固有天花板，也解释了为什么离线指标很高、实际游玩却容易撞。

**建议**：输入改为 4–8 帧堆叠（通道拼接或 3D 卷积 / GRU），或直接改用 RL / DAgger 式在线模仿。

---

### 🟠 P1-2　推理速度与控制频率

- `SHOW_HEATMAP = True` 且 `HEATMAP_UPDATE_INTERVAL = 0.01` —— 意味着**几乎每一帧都要做一次前向 + 反向**（Grad-CAM 反传），推理开销约为纯推理的 2–3 倍，而热力图窗口对实际操控毫无帮助。
- 截图线程 `time.sleep(0.02)` + ADB 截图延迟 + `Queue(maxsize=1)`（丢帧）叠加，端到端反应延迟很可能在 **200–500 ms** 量级。地铁跑酷需要的是 100 ms 级的反应。
- `ACTION_INTERVAL = 0.3` 定义了但**从未被使用**（死配置）。
- `KEY_DURATION = 0.01` 秒的按键时长偏短，雷电的按键映射可能偶发漏检。

**建议**：默认关闭热力图（改为按需开启）；把截图方式换成 `scrcpy` / `minicap` 直接读帧缓冲（可降到 10–30 ms）；实测端到端延迟并写入 README；按键时长调到 0.03–0.05 s。

---

### 🟠 P1-3　类别先验被抹平

真实游玩中 N（不操作）应占绝对多数，换道动作是稀疏事件。但数据集被刻意为每类各采集约 635 张，**先验完全均匀**。这会让 softmax 输出偏离真实场景分布，部署时的阈值（0.97 / 0.75 / 0.90 …）是在这个"人造均匀先验"下拍的，未必对应实际最优工作点。

**建议**：要么保留自然先验采集（并按类别加权损失），要么明确记录"先验被平衡过"，并在推理端重新做阈值标定（在真实游玩序列上扫阈值画 PR 曲线）。

### 🟡 P2-1　工程与可维护性

- **无 README、无 requirements.txt**，参数散落在各脚本顶部（`CROP_BOX` 在两处不一致就是这种散落的直接后果）。
- **无配置集中管理**：路径（`D:\leidian\LDPlayer9\adb.exe`、`D:\Anaconda\envs\wasd_local` 等）硬编码在多个文件里，换机器即失效。
- `trian.py` 结尾的 `plt.show()` 会阻塞进程；`num_workers=2` 在 Windows 上有额外进程开销，小数据集下常不如 0。
- `name.py` 的 `PREFIX = 'a4_'` 是遗留值，一旦运行会把所有文件重命名成 `a4_00001.png`，破坏现有命名。
- 训练脚本**未输出混淆矩阵 / 分类报告**，无法看出究竟哪两类容易混淆（尤其 S vs N）。
- 磁盘占用：`sj.zip` 1.04 GB（`sj\` 的备份）+ `paoku.zip` 197 MB + 4 个权重 97 MB ≈ 1.4 GB 冗余。
- 权重文件名无版本信息，建议改为 `effb0_sj_ep32_acc0.98_20260808.pth` 之类。

## 七、一句话总结

**数据管线完整、清洗意识良好（排除翻转增强、类别均衡化、去重检查），模型选择与训练流程规范，推理脚本的类别阈值 + 防抖 + Grad-CAM 设计也相当用心；主要短板集中在"评测可信度"和"时序"两处：随机划分 + 高度相关的游戏帧让 98% 的离线准确率明显虚高（零参数 1-NN 就有 76%），而"按键后截图"很可能让标签对准了动作发生后的画面、训练与推理的裁剪框又不一致 —— 这三点（时序对齐、裁剪统一、分组划分）是继续推进前必须解决的首要问题。**
