# 进阶说明：为什么效果不理想，以及怎么修

**这份文档什么时候看？** 当你已经跑通 [README.md](README.md) 的七步、
`6_评估效果.py` 的数字也看到了，但发现「模型动得太早」「连着按发不出来」这类问题时。

里面全是**实测数据**，不是推测。看不懂某些术语没关系，
每节开头都有一句大白话结论。

---

## 一、模型动作偏早（最典型的问题）

### 结论先说

**模型比人动手早，这是行为克隆的通病，不是你的数据坏了。**

### 为什么会这样

人的反应链是「看到障碍 → 判断 → 手指按键」，中间有 **200~300ms** 的生理延迟。
模型没有这个延迟，它是「看到画面 → 立刻输出」。

更麻烦的是训练数据的构造方式：正样本的输入窗口是**按键之前**的 6 帧
（跨度 167ms，结束于按键前 40ms）。也就是说模型学到的规律是
**「画面长这样 → 该按键了」**，而这个画面在真人看来其实**还没到该动的时候**。

后果：障碍还远就换道 → 等到真该动的时候，反而被部署端的 `--lockout-ms` 锁住了，按不出来。

### 实测有多早

用 `7_时序诊断.py` 在 594 样本 / exp01 上测（把输入窗口往前挪，看模型什么时候开始输出方向键）：

```
窗口结束于      正确率    输出方向键   正确且conf>.85
-146ms         76.8%      86.5%       64.7%     <- 数据只到这儿，再往前测不到
 -70ms         93.2%      95.7%       91.1%
 -40ms         94.4%      96.4%       91.3%     <- 训练时用的档位

77% 的按键，模型在能测到的最早时刻(-146ms)就已经决定了 —— 真实提前量更大。
```

```powershell
python 7_时序诊断.py          # 自己跑一遍看你的模型是什么样
```

### 四种应对手段

| 手段 | 说明 | 推荐度 |
|---|---|---|
| **`9_自动玩.py --delay-ms N`** | 让模型看 `now - N` 时刻的画面，动作整体后移 N 毫秒。不改模型、随时可调 | 应急可用，**但别超过 50** |
| `9_自动玩.py --calibrate` | 真实游玩时测出提前量，并给出 `--delay-ms` 的建议值 | 用来定 N |
| 提高置信度阈值 | **不推荐**。实测阈值提到 0.95 时，仍有一半是提前的，却让 12% 的换道直接漏掉 | ✗ |
| **补采数据 + 障碍还远负样本** | **根治**。见下一节 | ✓✓ |

## 二、已实施：800ms 前置窗口 + 「障碍还远」负样本

### 思路

既然问题出在「模型没机会学会等待」，那就**给它等待的样本**：
把每个样本往前存的时间从 300ms 拉长到 800ms，然后在训练时自动合成一类负样本 ——
**「障碍已经出现在画面里了，但还早，这时候应该 N」**。

### 现在的默认值（`collector/config.py`）

```python
save_pre_ms            = 800                  # 保存按键前 800ms（原来 300）
approach_neg_enabled   = True                 # 自动合成「障碍还远 -> N」负样本
approach_neg_end_ms    = (-250, -350, -500)   # 取哪几段更早的窗口
approach_neg_quiet_margin_ms = 250            # 这一段之前必须安静多久
```

### 几何关系（6 帧窗口跨度 167ms）

```
   -800 ...... -667 ...... -417 ... -250 ... -207 ...... -40 ... 0
   |<---------- 负样本「障碍还远」---------->|  |<-- 正样本 -->|
                                            43ms 空隙（零重叠）
```

负样本和正样本之间留了 43ms 空隙，画面**不重叠**，所以标签不会打架。

### 这个改动带来了什么

| 变化 | 影响 |
|---|---|
| 胶片条 22 帧 → **37 帧** | 单样本约 450KB → **750KB**；5000 样本约 3.7GB 磁盘 |
| 旧数据（`save_pre_ms=300`） | **完全兼容**：训练照跑，只是「障碍还远」负样本为 0，日志会提示 |
| 训练 | 两类负样本分别计数；`--no-approach-neg` 可单独关掉 |
| 评估 | `6_评估效果.py` 分开报「换道动画负样本 → N」和「障碍还远负样本 → N」 |
| 诊断 | `7_时序诊断.py` 现在能测到按键前 633ms（原来只有 146ms） |

> ⚠️ 这只是**让模型有机会学会等待**。边界具体落到哪儿，要用 `7_时序诊断.py` 对比
> 重新采集+训练前后的「最早在哪一档开始动」。如果边界没被推后，就把
> `approach_neg_end_ms` 里最靠近正样本的那一档（-250）再往 -207 靠一点重训。

> 想在不重新采集的前提下验证整条流水线，用 `tools/make_synth_dataset.py` 生成一份
> 假数据集（以 `_` 开头，不会被自动挑选选中）。

## 三、连按（WA / WS / AA）为什么发不出来

### 结论先说

**不是模型的问题，是部署端动作锁定挡掉的。**

### 数据长什么样

实测这批数据：

```
相邻按键间隔 <320ms 的          49 / 413 对 = 11.9%
最常出现的组合 W->S (跳完马上滚) 65 次，间隔中位 328ms，最小 192ms
同向连按 AA/DD/SS/WW           59 对，中位 1023ms（大多不快）
```

### 模型侧其实是好的

把第二个键的输入窗口单独拿出来测，**快连按的识别率反而更高**：

```
距上次按键        样本数    正确率    输出 N 的比例
<200ms             4     100.0%      0.0%
200-320ms         45      95.6%      2.2%
>700ms           199      93.0%      4.0%
```

### 问题在 `--lockout-ms`

它原本的含义是「发键之后 320ms 内不许再发**任何**键」，
而 `W->S` 的间隔中位正好是 328ms —— 一半都被挡掉了。

把真实按键序列跑一遍模拟：

| 方案 | 发不出去 | 比例 |
|---|---|---|
| 旧：全局锁定 320ms | 47 / 413 | **11.4%**（几乎全是 W→S） |
| 新：同方向锁定 320ms + 全局间隔 80ms | 2 / 413 | **0.5%**（A→A 253ms、D→W 38ms） |

现在 `--lockout-ms` **只锁同一个方向**：A 之后再按 A 要等 320ms
（防换道动画里重复触发），但 A 之后按 D/W/S **立刻放行**（那是新决策）。
另外加了 `--min-gap-ms 80` 防同一瞬间连发。

## 四、⚠ `--delay-ms` 和连按是冲突的

`--delay-ms` 让模型看更早的画面来压后动作，但**快连按的第二个键本来就落在上一个键的换道动画里**，
画面再往前挪，模型就找不到依据了：

```
--delay-ms      快连按正确率     慢间隔正确率
0                 95.9%          93.0%
30                95.9%          92.0%
81                65.3%   <<<     87.9%
106               49.0%   <<<     82.9%
```

**所以 `--delay-ms` 别超过 50ms**（程序超过时会告警）。

要彻底解决「动作偏早」，靠的是**补采数据**（`save_pre_ms=800` + 障碍还远负样本），
而不是在部署端找补偿 —— 部署端的任何补偿都一定会牺牲连按。

## 五、注意力可视化：模型到底在看哪里

### 结论先说

**可以看到，而且代价很低** —— 不需要额外依赖，只多一次反向传播。

```powershell
python 8_注意力可视化.py                 # 离线：每类挑一个最有代表性的样本出图
python 8_注意力可视化.py --live          # 实时：Grad-CAM 叠在当前画面上
python 8_注意力可视化.py --id A_000018   # 只看某一个样本
```

一次反传同时拿到三样东西（实现在 `collector/attention.py`，没用 `pytorch-grad-cam` 之类的第三方库）：

| 内容 | 含义 |
|---|---|
| **Grad-CAM**（7x7 上采样到 224） | 证据来自画面的哪个**位置**。位置准，但分辨率受最后一级特征图限制，会有点块状 |
| **输入梯度显著图**（224x224） | 原生分辨率，更细但很噪，适合看边缘/纹理层面的响应 |
| **逐帧消融** | 把某一帧置零，看置信度掉多少个百分点 —— 直接回答「这 6 帧模型各用了多少」 |

> ⚠️ 两个坑：① **必须用 float32**，`9_自动玩.py` 为了速度转了 half，反向传播会出 NaN；
> ② 热力图**不能直接拉满整帧** —— 输入变换里有 `Resize + CenterCrop`，
> 不还原的话热区会上下错位（`cam_to_frame()` 做的就是这件事）。

### 实测：热区语义完全正确（exp01，594 样本）

每类挑一个最自信的样本：

| 类别 | 热区落在哪 | 是否合理 |
|---|---|---|
| A（左移） | 左前方障碍 / 目标车道 | ✓ |
| D（右移） | 右前方列车 | ✓ |
| N（不动） | 正前方骑手（要避开的对象） | ✓ |
| S（下滚） | 头顶横杆 | ✓ |
| W（上跳） | 前方光带 + 角色 | ✓ |

出图在 `runs/exp01/attention/`，`attention_grid.png` 是 5 类拼在一起的总图。

### 实测：6 帧早融合确实在用

在测试集 68 个方向键样本上，只保留部分帧、其余置零：

```
保留 1 帧    8.5%
保留 2 帧   44.4%
保留 3 帧   66.3%
保留 4 帧   73.6%
保留 5 帧   78.4%
保留 6 帧   82.4%
```

单调递增，说明多帧输入不是装饰。**但去掉任意单帧只掉 0~7.4 个百分点**，
说明帧与帧之间高度冗余（166ms 窗口内画面几乎一样）。

> 想让它学到「运动 / 接近速度」，得把帧**拉开**（调大 `input_stride`），而不是加密。
> 这也可能是「动作偏早」的一个成因：模型看到的 6 帧几乎等价于 1 帧，判断不了障碍还有多远。

### 实时模式

`--live` 每帧多做一次反向传播，实测约 **20fps**（够看，但不适合边看边玩）。

## 六、两种「现在是不是在跑酷」的判断方式

采集器靠这个来决定记不记录。两种方式二选一：

| | 画面判断（默认） | **内存读取（`--hook-state`，推荐）** |
|---|---|---|
| 判据 | 帧间差异：画面在动 = 在跑酷 | 游戏自己的变量 `_isInPlaystate` / `_isAlive` |
| 开局识别 | 等画面动起来，约 0.5s | 精确 |
| **撞车时刻** | 等画面静止，**慢 3~4 秒** | `alive` 由 1 变 0 的**那一帧** |
| 回滚策略 | 猜「最后 4 秒」 | 从撞车时刻往前 0.5s |
| 依赖 | 无 | 模拟器 + adb + frida-server + 状态服务 |
| 失效场景 | 有动画的弹窗会误判 | 游戏更新版本后类/字段偏移可能变 |

用法就是给采集器加一个开关：

```powershell
python 2_采集数据.py --session run01 --hook-state
```

服务没起来的话它会自动拉起，细节见 [常见问题.md](常见问题.md) 的「B. 状态服务」一节
和 [tools/README.md](tools/README.md)。

## 七、游戏速度越来越快怎么办

《地铁跑酷》的速度随存活时间上升，所以「开头几秒的画面」和「跑了一分钟的画面」
分布完全不同。如果数据里全是慢速段，模型一进高速段就会失效。

采集器会记录**每个样本的速度**，然后：

```powershell
python 4_速度覆盖度.py dataset/run01      # 看覆盖度报告
```

覆盖均匀时会说 `[OK] 速度覆盖看起来是均匀的`；
不均匀时会警告，比如：

```
[警告] 最高速段只占 3.8%（建议 >= 10%）—— 高速样本不足，模型上线后进高速段会失效
```

如果补采来不及，还可以在训练时**按速度重加权**（默认关闭）：

```powershell
python 5_训练模型.py --session dataset/run01 --out runs/exp01 --speed-balance 0.5
```

强度 0 表示不重加权，1 表示把速度分布完全拉平。实测对「94% 慢速 + 6% 高速」的数据，
慢速样本被降到 0.35 倍权重、高速升到 9.22 倍。

> 注意：重加权只是缓解，**能补采就补采**。高速样本被放大 9 倍意味着它在梯度里被重复学习，
> 如果那几条样本本身质量不好，反而会学歪。

**本项目目前最大的短板就在这里**：现有几批数据的速度中位数只有约 10 px/秒，
最快也就 27~41 px/秒，最高速段占比不到 1%。所以模型在高速段基本必死。
**补采时一定要玩得久。**

## 八、N 类（「别动」）的三个来源

N 是最难的一类 —— 因为「什么都不做」不是一个动作，没法模仿，只能靠构造。

| 来源 | 怎么来的 | 治什么病 |
|---|---|---|
| **来源 1：手动按 `n`** | 你玩的时候觉得「这时候不该动」，就按一下 `n`，程序记一个 N 样本 | 提供真实的「等待」样本 |
| **来源 2：换道动画合成** | 训练时自动构造：按键之后 +200ms / +350ms 的画面，此时角色**已经在换道动画里**，标签 N | 治「移动过程中重复触发」 |
| **来源 3：障碍还远合成** | 训练时自动构造：按键之前 -250 / -350 / -500ms 的画面，此时障碍已出现但还早，标签 N | 治「动作偏早」 |

来源 2 和 3 都是**训练时现算的**，不占磁盘、不用你手动采 ——
前提是 `save_pre_ms` / `save_post_ms` 够长（已经是 800 / 400）。

细节（比如空档判定、quiet margin）见 [collector/README.md](collector/README.md)。

## 九、一句话总结现在的短板

| 短板 | 影响 | 出路 |
|---|---|---|
| 高速段样本不足（<1%） | 进高速段基本必死 | **补采**，每局玩久一点 |
| 6 帧窗口内画面高度冗余 | 模型判断不了障碍距离，容易动手太早 | 调大 `input_stride` 把帧拉开，重训 |
| `--delay-ms` 与连按冲突 | 只能二选一 | 靠补采根治，别指望部署端补偿 |
| 模型没有人的反应延迟 | 动作系统性偏早 | 见第一节 |

**这四条里，前两条只能靠「多采、采久、重新训练」解决，没有捷径。**
