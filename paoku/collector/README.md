重写自 `caiji.py` / `shuju.py`，目标是彻底解决旧方案的三个问题。

## 一、旧方案错在哪

| 问题 | 旧做法 | 后果 |
|---|---|---|
| **标签与画面错位** | 按下按键 → 立刻 `adb exec-out screencap -p` | 截图有 100~300ms 延迟，存下来的是**动作已经发生之后**的画面。模型因此学到"角色已经在往左挪 → 该按 A"，部署时角色一开始挪动它就**再次输出 A** —— 这就是"在移动过程中还会再识别再移动"的直接成因 |
| **单帧无时序** | 每个样本只有一帧 | 无法表达速度/时机，也分不清"该换道"和"正在换道" |
| **抓帧链路脆弱** | 依赖 ADB | 本机 LDPlayer 的 `adb shell` / `screencap` 会长时间挂起（实测 `screencap` 超时 20s）；且必须模拟器在前台未被遮挡 |

## 二、新方案怎么做的

```
                      ┌──────────────────────────────────────┐
   抓帧线程 (~40fps)  │  PrintWindow 抓窗口 → 裁剪 → 缩放    │
                      └───────────────┬──────────────────────┘
                                      ▼
                          ┌───────────────────────┐
                          │ 环形缓冲 (最近 5 秒)  │  ← 只在内存里
                          └───────────┬───────────┘
                                      │  按键只记一个"时间戳"
             按下 A ────────────────► │
                                      ▼
                   正常样本: 按键前 [-233ms ~ -67ms] 的连续 6 帧  -> 标签 A
                   合成样本: 按键后 [ +33ms ~ +200ms] 的连续 6 帧  -> 标签 N（换道动画中）
                   合成样本: 按键前 [-417ms ~ -250ms] 的连续 6 帧  -> 标签 N（障碍还远）
                   整段 [-800ms ~ +400ms] 存成一张"胶片条"JPEG + 逐帧时间戳
```

三个要点：

1. **抓帧永远发生在按键之前**。按键只是往缓冲里打时间戳，事后回溯取帧。
   一帧只有在被抓取之后才会进入缓冲，而时间戳是在抓取**之前**打的，
   所以要被选中就必须满足 `t <= 按键时刻 - 40ms` —— 那时候"动作之后的画面"根本还不存在。
   这不是概率问题，是时序上的不可能。

2. **每个样本保存 37 帧连续画面**（-800ms ~ +400ms，含逐帧时间戳）。
   按键前那 800ms 是刻意留长的：只有存了它，才能事后合成「障碍已出现但还不该动 → N」
   的负样本，治模型「动作偏早」（见第七节来源 3）。
   想改"用几帧""往前偏移多少""负样本采样点"，**都不需要重新采集**，离线重切即可。

3. **后置窗口还用来合成 N 类负样本**（见第七节），这是治"重复触发"的关键。

## 四、抓帧后端实测（本机 LDPlayer9 + RTX4060）

| 后端 | 速度 | 窗口被遮挡时 | 结论 |
|---|---|---|---|
| `printwindow` | **12 ms/帧（~82fps）**，实测稳定 40~56fps | 正常 | **默认，推荐** |
| `bitblt` | 2 ms/帧（~500fps） | 可能抓到遮挡窗口的画面 | 可选 |
| `adb screencap` | 超时/挂起 | — | 已弃用 |

|---|---|

## 六、数据格式

```
dataset/<session>/
  A/  D/  N/  S/  W/
  meta.jsonl        每个样本一行
  session.json      本次采集用的完整配置
  summary.json      结束时统计
  debug/            F7 导出的调试条
```

一张 `*.jpg` = **横向胶片条**：从左到右时间顺序，每帧 `240x293`，帧间有 `sep=2` 像素白色分隔线。

```json
{"id":"A_000123","label":"A","kind":"key","src_key":"a","file":"A/A_000123.jpg",
 "t_anchor":1723541234.567,
 "frame_times_ms":[-300.0,-266.7,...,400.0],
 "n_frames":22,"frame_w":240,"frame_h":293,"sep":2,
 "requested_pre_ms":300,"requested_post_ms":400,"truncated_window":false,"capture_fps":40.0}
```

`frame_times_ms` 是每帧相对按键时刻的毫秒偏移（负数 = 按键之前）。
`kind` 为 `key`（你按下的键，`src_key` 告诉你按的是哪个）或 `auto_n`（空闲自动补的 N，默认已关闭）。
N 类样本的 `src_key` 是 `n`。

## 七、类别设计：N 类是怎么来的（重点）

采集 5 类：`labels = ("A","D","N","S","W")`。N = "此刻正确的动作是什么都不做"。

**N 有两个来源，缺一不可：**

### 来源 1：你手动按 `n` 键标记的画面

**和 WASD 一样 —— 按下才记。** 什么时候按？当你判断「此刻正确的动作就是什么都不做」的时候
（前方一片空旷、只需要直行、没有需要提前换道的东西）。

用的回溯取帧逻辑和方向键**完全相同**，所以时序一样正确：取的是按 n 之前的 6 帧。

> `n` 在 Subway Surfers 里没有按键映射，按下去游戏不会有任何反应，只是给采集器打标记。

**为什么不用「空闲时自动补」**（默认已关）：

* 自动补在菜单、弹窗、死亡结算里也会采到 N（现在有限速和避让，但仍然不如手动干净）
* 采出来的帧高度重复 —— 实测类内近邻 ≤2.0 的「双胞胎帧」比例，N 类是 **13%**，所有类里最高
* 手动按能保证每个 N 都是你**有意**标记的

想恢复自动补：`n_auto_enabled = True`，或采集时按 `F9` 临时开。

**但开了自动补，它会限速，并主动避开 WASD 按键附近的那几帧：**

| 参数 | 默认 | 作用 |
|---|---|---|
| `n_auto_interval_ms` | `1500` | 两次自动 N 至少隔 1.5 秒。原来 400ms = 2.5 个/秒，N 会被灌爆，模型就偏向"什么都不做" —— 该换道的时候不动，直接撞死 |
| `n_idle_after_ms` | `500` | 距离上一次方向键至少 0.5 秒，才算"真的空闲了" |
| `n_suppress_after_key_ms` | `500` | **按键后避让**。N 样本喂给模型的是该点往前 207ms~40ms 的 6 帧；避让 500ms 保证这 6 帧整体落在换道动画**结束之后**，不和 WASD 按键样本的画面重叠 |
| `n_guard_after_key_ms` | `350` | **按键前避让**。候选点选中后先不落盘，再等 0.35 秒做确认；这期间如果又按了 WASD，说明刚才那一刻其实是"马上要按键"的前奏，正确标签是按键而不是"什么都不做"，直接丢掉 |

实测（假时钟仿真：20 秒、9 次按键）：

```
改之前  interval=400   idle=200   只挡按键后 150ms
        自动 N 41 个（2.05 个/秒），其中 6 个贴在上一次按键后仅 0.22~0.30 秒处

改之后  interval=1500  idle=500   按键后避让 500ms + 按键前避让 350ms
        自动 N 13 个（0.65 个/秒），全部满足：距上一次按键 >=0.5s、距下一次按键 >=0.35s
```

被丢掉的候选会计入 `summary.json` 的 `auto_n_dropped` 字段，采集结束时也会打印出来。

> 注意：这套避让只管**自动补的 N**。你用 `n` 键手动标记时，采集器不会拦你 ——
> 那是你的明确判断。但手动 `n` 也别紧贴着 WASD 按，否则同一批画面会同时出现
> A/D 和 N 两种标签，模型会学糊涂。

### 来源 2：训练时从"换道动画"自动合成的画面 ← 治重复触发的关键

按键之后 `save_post_ms`(400ms) 内保存的帧，显示的是**角色已经在换道动画中**。
把这些帧当作模型输入、标签设为 N，就教会了模型：

> "角色已经在动了 → 输出 N（别再按）"

**这一条直接治你遇到的"在移动过程中再识别再移动"。**

实现（`dataset.py`）：

```python
select_window_indices(meta, frames, stride, end_offset_ms)
#   正常样本: end_offset_ms = -40      -> 输入帧全部在按键之前
#   合成负样本: end_offset_ms = +200/+350 -> 输入帧全部在换道动画期内
```

配置：

```python
animation_neg_enabled  = True        # 总开关（训练时 --no-anim-neg 可关）
animation_neg_end_ms   = (200, 350)  # 输入窗口结束于按键后多少 ms（取多个采样点）
animation_neg_min_gap_ms = 700       # 空档判据，见下
```

**空档判据很重要，否则会引入标签噪声**：只有当这个按键之后至少 700ms 内**没有再按任何键**，
才认为"当时确实不该动"。否则那段时间人其实又做了决策，硬标成 N 是错的。
（`dataset.py` 里的 `build_animation_negatives()`）

> 代价：合成负样本不占额外磁盘（复用同一张胶片条，只是换一个取帧窗口），
> 但会增加训练样本数。大致每 1 个按键样本 → 2 个 N 负样本。

### 来源 3：训练时从「障碍已出现但还不该动」自动合成的画面 ← 治动作偏早

上面来源 2 治的是「已经在动了还按」，这一条治的是反过来的毛病：**障碍还远就动手**。

模型只学过「按键前那一小段画面 → 动作」，从没见过「障碍已经出现、但还没到该动的时候」，
于是把动作一路往更早的时刻泛化。用 `7_时序诊断.py` 量过：77% 的按键，模型在能测到的
最早时刻（按键前 146ms）就已经输出动作了，真实提前量更大。

做法和来源 2 完全对称，只是窗口取在**按键之前**：

```python
select_window_indices(meta, frames, stride, end_offset_ms)
#   正常样本:   end_offset_ms = -40        -> 按键前 [-207, -40]
#   换道动画负样本: end_offset_ms = +200/+350 -> 按键后
#   障碍还远负样本: end_offset_ms = -250/-350/-500 -> 更早的那几段窗口，标签 N
```

配置：

```python
approach_neg_enabled          = True            # 总开关（训练时 --no-approach-neg 可关）
approach_neg_end_ms           = (-250, -350, -500)  # 窗口结束于按键前多少 ms
approach_neg_quiet_margin_ms  = 250             # 安静期余量，见下
save_pre_ms                   = 800             # 必须够长，否则取不到这些窗口
```

**两个必要条件**（`dataset.py` 里的 `build_approach_negatives()`）：

1. **窗口必须完整**：`save_pre_ms` 要够长。6 帧窗口跨度 167ms，所以 800ms 的保存窗口
   最早只能取到按键前 633ms 的窗口；旧数据（300ms）会**自动跳过**，不会报错也不会产生垃圾样本。
2. **这一段之前必须安静**：上一个按键要在窗口起点再往前 250ms 以上。
   要求 = `|偏移| + 窗口跨度 + 250ms`（如 -500 档要求前面安静 916ms）。
   否则那段画面其实是上一次动作的动画，硬标成 N 会和正样本打架。

> 正负样本窗口**零重叠**：正样本覆盖 [-207, -40]，最近的负样本覆盖 [-417, -250]，
> 中间留 43ms 空隙。这是把决策边界往「该动」那一刻压的关键 —— 负样本离正样本越近，
> 边界压得越紧。
>
> 注意：这一条只是**让模型有机会学会等待**，边界具体落在哪儿要靠重新采集后
> 用 `7_时序诊断.py` 对比「最早在哪一档开始动」来验证。

### 想改成只收 WASD（不要 N）

把 `labels` 改回 `("A","D","S","W")` 即可。但**不推荐**：没有 N，模型必须在 4 个方向里
挑一个，没有任何"别动"的输出可用，"重复触发"就只能靠部署端的动作锁定硬压。

## 八、怎么改"用几帧 / 往前偏移多少"

改 `config.py`（或写 JSON 覆盖）：

```python
input_frames = 6            # 输入连续帧数
input_end_offset_ms = 40    # 输入窗口结束于按键前多少毫秒
input_stride = 1            # 输入帧之间的步长
```

**改完不需要重新采集**，直接重新训练即可 —— 只要不超过保存窗口范围。
想覆盖更长的时间跨度，把 `save_pre_ms` / `save_post_ms` 调大。

## 九、训练侧怎么接

```python
from collector.config import Config
from collector.dataset import (MultiFrameDataset, load_sessions, negatives_for_subset,
                               build_train_transform, build_eval_transform, split_indices)

cfg = Config.load("collector/myconfig.json")
samples = load_sessions(["dataset/run01", "dataset/run02"])
labels = ["A", "D", "N", "S", "W"]

sp = split_indices(samples, mode="time_balanced")     # 不要用 mode="random"

# 合成"换道动画中 -> 不该动"的负样本（先在全量上判空档，再映射到子集）
neg_train = negatives_for_subset(samples, sp["train"], cfg, labels)

train_ds = MultiFrameDataset([samples[i] for i in sp["train"]], cfg,
                             build_train_transform(224), labels=labels, negatives=neg_train)
```

`__getitem__` 返回 `(x, y)`，其中 `x` 形状是 `(input_frames*3, 224, 224)`
（多帧在通道维早融合）。对应的模型改造：

```python
import torch.nn as nn
from torchvision import models

def build_model(in_frames, num_classes, pretrained=True, weights_path=None):
    m = models.efficientnet_b0(weights=None)
    if weights_path:                       # 从本地文件加载 ImageNet 权重
        m.load_state_dict(torch.load(weights_path, map_location="cpu"))
    elif pretrained:
        m = models.efficientnet_b0(weights=models.EfficientNet_B0_Weights.IMAGENET1K_V1)
    old = m.features[0][0]                 # Conv2d(3, 32, 3, stride=2)
    new = nn.Conv2d(3 * in_frames, old.out_channels, old.kernel_size,
                    old.stride, old.padding, bias=False)
    with torch.no_grad():                  # 用预训练权重复制并平均来初始化
        new.weight.copy_(old.weight.repeat(1, in_frames, 1, 1) / in_frames)
    m.features[0][0] = new
    m.classifier = nn.Sequential(nn.Dropout(0.3), nn.Linear(1280, num_classes))
    return m
```

> 用 `torchvision.transforms.v2` 的变换对 `(T,C,H,W)` 张量做增强时，**所有帧共用同一套
> 随机参数**，不会出现每帧各裁一块的时序错位。旧版的 `RandomResizedCrop` 是逐帧独立做的。

## 十、注意事项

1. **模拟器不要被缩放**，安卓画面必须是原生 `720x1280`。采集器按"客户区内水平居中、
   底部对齐"自动推算画面位置（实测顶部工具条 35px、左右边框各 1px），自检会把
   裁剪框画在整窗截图上供人工确认。
2. **训练和部署必须用同一套参数**（`game_crop` / `frame_w` / `input_frames` /
   `input_end_offset_ms` / 抓帧后端）。`session.json` 会把配置原样存下来，部署时读它即可。
3. 采集时不要让模拟器窗口最小化；PrintWindow 在被遮挡时没问题，但最小化时内容会停住。
4. 自检报"画面完全没有变化"时，先重启模拟器。本机已出现两次模拟器卡死
   （画面零变化 + 虚拟机进程消失 + `adb devices` 为空）。
5. 磁盘：每样本约 750KB（37 帧胶片条）。采 5000 个样本约 3.7GB；
   本机磁盘上按 750KB/样本堆着，攒够再一起训练。

| 质量守护 | 无 | 卡死检测 / 黑屏检测 / 静态样本检测 |

## 十二、采集时操作失误怎么办

三级防线：**预防 → 现场撤销 → 事后复核**。

### 第一级：预防

| 手段 | 说明 |
|---|---|
| `F8` 暂停/继续 | 过场动画、菜单、死亡结算、商店界面时按一下。**最重要的习惯** |
| 120ms 防抖 | 同一类别 120ms 内只记一次，按住不放或手抖连按不产生重复样本 |
| 卡死检测 | 画面连续 60 帧完全不变就告警 |

### 第二级：现场撤销（`X` 键，按个数删）

```
[撤销] 删掉 5 个样本；最近一个是 16:54:00
       当前各类别: A:132  D:128  N:140  S:95  W:141
       再按一次继续往前删 5 个（这一串还能按 4 次）
```

- **按一次删掉最近落盘的 5 个样本**（按采集时间倒序），连按 `X` 就一批一批往前退
- **连按最多 5 次**，第 6 下会提示 `已经连按 5 次了，先停一下`
- **停手 5 秒后再按，次数自动重新计满** —— 这不是"整场总额度"，限制的只是"当下这一串连按"

  | 参数 | 默认 | 含义 |
  |---|---|---|
  | `undo_count` | `5` | **一次删几个样本** |
  | `undo_max_times` | `5` | 一次连按最多几下（5×5 = 最多 25 个） |
  | `undo_reset_after_ms` | `5000` | 距上次成功撤销超过这么久，额度重新计满 |

> ⚠️ **为什么不是"按时间删 10 秒"**（旧做法，已废弃）：
> 旧逻辑是"删掉撤回点往前 10 秒内的所有样本"。但撤回点往回退的同时，
> "现在"还在往后长 —— 如果两次按 X 之间又采了很久，一次就会吞掉整整那一段。
> 实测有人按一次 X 删掉了 **229 个样本**（中间隔了 9 分钟没按 X）。
> 改成按个数删之后，每次删多少完全可预期。

- 撞车后自动回退（`crash_rollback_ms`）仍然是按时间的，走内部通道、**不占额度**；
  没删到样本的那一下（已经退到采集起点）也不计数
- **同时**删除 JPEG 文件和 `meta.jsonl` 里对应的行，并回收编号（不留空洞）
- 比这批更晚、还没落盘的样本（按键后 400ms 内的）也会一起丢掉

> 🔒 **为什么撤销要加锁**：`meta.jsonl` 的句柄、`self.written`、类别计数被 **4 个线程**共用 ——
> 写线程（落盘）、键盘线程（按 X）、状态检测线程（撞车自动回滚）、主线程（退出）。
> 早期版本 `_rewrite_meta()` 是 `flush → close → 重新 open`，两个线程同时进来时后一个会
> flush 到已经关掉的句柄，抛 `ValueError: I/O operation on closed file`，把按键回调整个打崩。
> 现在：① `_rewrite_meta()` 改成原地 `seek(0) + truncate()`，不再关文件；
> ② 用一把 `_meta_lock`（RLock）把 `_flush` / `_rollback` / `_undo` / `_recount` / `_finalize` 串起来；
> ③ 加锁顺序固定 `_meta_lock → pending_lock`，不会死锁。

### 第三级：事后复核（`3_复核数据.py`）

```
[12/3184] A_000137  label=A  kind=key  142KB  motion=18.4
green = model input (6 frames, all BEFORE the key press)   blue = hold-window (N negative)
red = key press t=0
  -300  -267  -233  -200  -167  -133  -100   -67   -33    +0   +33   +67  +100
[n]ext [p]rev [d]elete [f]ind suspect   1=A  2=D  3=N  4=S  5=W   [q]uit
```

| 按键 | 作用 |
|---|---|
| `n` / 空格 / → | 下一个 |
| `p` / ← | 上一个 |
| `d` / Delete | **删除**这个样本 |
| `1` `2` `3` `4` `5` | **改标签**（文件自动移到对应类别目录） |
| `f` | 跳到下一个可疑样本 |
| `q` / Esc | 保存退出（改动即时写盘） |

**自动可疑检测**：打开时逐个样本比较帧内容，找出"整个窗口画面都没变"的废样本
（误采菜单 / 模拟器卡死）。真实跑酷画面 motion 值通常 15~40，静止画面接近 0。

### 常见失误对照表

| 失误 | 怎么处理 |
|---|---|
| **按错键**（想按 A 按了 D） | 当场 `X` 撤销，或事后按 `1~5` 改标签 |
| **误采到菜单/结算画面** | 事后按 `f` 跳到可疑样本批量删 |
| **模拟器卡死采了一批废的** | 采集器会告警；事后 `f` 批量删 |
| **手抖连按** | 防抖已处理 |
| **整段都不想要** | `X` 连按往前退（一下 5 个、一次连按最多 5 下 = 25 个，停手 5 秒可以接着删）；整段不要就直接删掉会话目录重采 |

### 一个采集器解决不了的噪声（需要人工留意）

**"按了键但游戏没反应"**：角色已经在最左道了你还按 A，游戏毫无反应，但采集器照样记了
一个 A 标签。这个标签是错的 —— 这种画面下正确动作是"什么都不做"。

复核时留意这类画面：**该方向已经没有路可换了**，看到就按 `d` 删。

## 十三、游戏速度越来越快怎么办

地铁跑酷的速度随存活时间上升。同一个障碍，在 1x 和 3x 速度下**画面完全不同**。
这会带来两个不同的困难，必须分开对待：

| | 困难 | 连续帧能不能帮忙 |
|---|---|---|
| **① 视觉分布漂移** | 同样"前方 300px 有障碍"，不同速度下画面不一样（6 帧窗口内的位移差好几倍） | ✅ **能**。窗口内的视差本身就是速度的编码，模型可以直接"看见"速度 |
| **② 决策时限缩短** | 速度越快，必须越早动手 | ✅ 能。只要数据覆盖了高速段，人的标签自然编码了"更早动手" |

所以连续帧是解药，**但前提是训练数据覆盖了整个速度区间**。如果你只在每局前 30 秒采集，
模型就永远没见过高速画面，上线后一进高速段就废 —— 这才是真正会翻车的地方。

### 采集器做了什么

1. **每个样本落盘时记录速度**（`meta.jsonl` 里的 `speed_px_s`，单位像素/秒）。
   方法：相邻帧的相位相关（phase correlation）。实测与真实滚动速率的相关系数 **0.9998**。

2. **状态栏实时显示速度**，采集时你能直接看到当前跑多快：

```
[18:42:13] 抓帧  40.2fps  速度    482px/s  缓冲  200帧  A:132  D:128  N:140  S:95  W:141  跳过 0  采集中
```

### 采完检查覆盖度

```powershell
python -m collector.coverage dataset/run01 dataset/run02
```

输出示例（每档柱状图 + 自动告警）：

```
  dsh_spd_B            样本    53（按键 53）  n=53  最小 120  5% 120  中位 120  95% 491  最大 1199 px/s
      速度分布 (px/s):
           120 -    228     50   94.3%  ########################################################
           228 -    336      0    0.0%
           ...
          1091 -   1199      1    1.9%  #
      [警告] 最高速段只占 3.8%（建议 >= 10%）—— 高速样本不足，模型上线后进高速段会失效
      [警告] 最低速段占了 94.3% —— 前面几秒采太多，建议每局玩久一点再开始记
```

覆盖均匀时它会说 `[OK] 速度覆盖看起来是均匀的`。

### 训练时按速度重加权

如果补采来不及，可以先用重加权缓解（默认关闭）：

```powershell
python 5_训练模型.py --session dataset/run01 --out runs/exp01 --speed-balance 0.5
```

> 预训练权重默认走 torchvision 缓存自动下载；要完全离线就用 `--pretrained-weights` 指到
> 本地 `.pth`，或者用 `--no-pretrained` 直接关掉。

强度 0 表示不重加权，1 表示把速度分布完全拉平。实测对"94% 慢速 + 6% 高速"的数据，
慢速样本被降到 0.35 倍权重、高速升到 9.22 倍。

> 注意：重加权只是缓解，**能补采就补采**。高速样本被放大到 9 倍意味着它在梯度里被重复
> 学习，如果那几条样本本身质量不好，反而会学歪。训练脚本会在速度覆盖不足时打印警告和
> 建议命令。

### 采集建议（重要）

* **每局尽量玩久一点**，不要在开局几秒就退出。速度上来之后才是最有价值的数据。
* **高速段至少占 10% 以上的样本**。一局玩到撞死，后面那段高速期通常就够。
* 多分几局、用不同的 `--session` 存，采完用 `coverage` 一起检查。
* 如果发现覆盖不均，优先补采而不是靠重加权硬扛。

### 还有一个可选的强化手段（暂未启用）

既然速度已经被估出来，也可以做**按速度缩放的输入窗口**：高速时用更短的时间窗，
让窗口覆盖的"距离"保持恒定，从而让输入分布在速度维上更一致。

不过固定时间窗 + 连续帧本身已经自洽（窗口里既有场景也有视差），所以默认没开。
如果实测发现高速段仍然不稳，可以再加这一层。

## 十四、游戏状态自动检测（开局自动录、撞车自动停）

### 为什么不用 Frida

雷电用 **libhoudini** 把 ARM 翻译成 x86 执行，`libil2cpp.so` 的映射是 `r--p`
（**没有执行权限**）。实测结论：Frida 看不到 ARM 模块、从 x86 agent 调 ARM 导出函数会挂死、
Interceptor 挂钩无效。所以运行时 hook 这条路走不通，**只能从画面判断**。

（详见 `C:\Users\Tanlv\Desktop\ds_hr\ld_apk\out\REPORT_subwaysurf_infinite_jump_fix.md`）

### 判据：帧间差异

跑酷时整条跑道在向前滚动，相邻帧差异很大；菜单、弹窗、Continue? 死亡界面、
结算大厅都是静止的。实测（64x64 灰度，只取画面上部 72%）：

| 画面 | 帧间差异 |
|---|---|
| 静止的菜单 / 弹窗 | **0.45** |
| 真实跑酷 | **10 ~ 40** |

状态机带迟滞，避免抖动：

```
静止 --连续 state_on_ms(500ms) 都 > 5.0-->  跑酷中
跑酷 --连续 state_off_ms(1200ms) 都 < 1.5-->  静止
```

### 它怎么满足三个需求

| 需求 | 实现 |
|---|---|
| **游戏开始时才录制** | 倒计时/菜单期间差异很小 -> 判定静止 -> 不记录；跑道一开始滚动 -> 自动开始 |
| **撞车被警察抓住那段不记录** | 一局结束（跑酷 -> 静止）时**回滚删掉最后 4 秒**的样本。撞车 -> 被警察抓住 -> 弹出 Continue? 大约就是 3~4 秒 |
| **失败自动暂停、等重新开始再继续** | 状态切到静止即自动暂停；检测到下一局开局自动恢复，不需要按任何键 |

状态栏实时显示当前状态和差异值：

```
[18:42:13] 抓帧40.2fps 速度 482px/s 状态跑酷中(18.4) 采集中   A:132 D:128 ...
[18:43:02] 抓帧39.8fps 速度   0px/s 状态静止  ( 0.4) 等开局中 A:132 D:128 ...
```

一局结束时控制台会打印：

```
[状态] 本局结束（帧间差异 0.6）-> 自动暂停
       已回滚最后 4000ms 的 11 个样本（撞车 + 警察抓住那段，标签没有意义）
       重新开始游戏后会自动继续采集
```

### 和手动 F8 的关系

两者是**与**的关系：F8 暂停时无论自动状态如何都不记录；F8 恢复后仍要等自动检测到开局才记。
想完全回到手动模式：

```powershell
python 2_采集数据.py --no-auto-state
```

### 阈值怎么调

默认值（>5.0 开局 / <1.5 结束）是保守的 —— **宁可多录也不漏录**，因为误判成"静止"
会导致完全不记录，代价比多录一些菜单画面大得多。

采集时盯着状态栏括号里的数字：

* 跑酷中应该稳定在 **10 以上**。如果经常掉到 5 以下（阈值偏高会漏录），调小：
  ```powershell
  python 2_采集数据.py --motion-on 3.0
  ```
* 菜单/弹窗如果超过 5（阈值偏低会误录），调大：
  ```powershell
  python 2_采集数据.py --motion-on 8.0
  ```
* 一局结束时回滚不够（警察画面还留着）就加大：
  ```powershell
  python 2_采集数据.py --rollback-ms 6000
  ```

### 已知局限

* **有动画的弹窗可能被误判成跑酷中**。此时你在菜单里不按方向键，所以不会产生按键样本；
  但如果你开了「空闲自动补 N」（F9），它会补进一些菜单画面。复核时用 `f` 键跳可疑样本删掉即可。
默认是**手动按 n**，不存在这个问题。
* 抓帧约 40fps，状态切换判定精度约 ±50ms。

## 自动拉起状态服务（推荐用法）

采集器现在会**自己把状态服务拉起来**，不需要你手动开第二个窗口：

```powershell

--session run01 --hook-state

# 或者命令行
python 2_采集数据.py --session run01 --hook-state
```

启动时会打印：

```
[IL2CPP] 状态服务没在跑，用 D:\Anaconda\envs\wasd311\python.exe 自动拉起 ...
[IL2CPP] 状态服务已就绪 (127.0.0.1:47800)，用时 3.0s
[IL2CPP] 状态服务已连接  inst=0xade28820  当前 inPlay=0 alive=1
```

它做的事：检查 47800 端口 -> 没在跑就用 `wasd311` 的解释器新开一个控制台窗口跑
`tools/state_server.py` -> 等端口就绪 -> 连上去。

状态服务启动时还会自动检查 **adb server / 设备连接 / frida-server / 端口转发**，缺什么补什么：

```
[前置] 检查模拟器 / adb / frida-server
      adb 设备: emulator-5554	device
      frida-server: 运行中
      端口转发: tcp:27042 -> 设备
```

> **模拟器每次重启后 frida-server 都会丢**，所以这一步不能省。

如果自动拉起失败，会打印提示并**自动回退到画面判断**，采集不会因此失败。

### 为什么当初是新建 wasd311 而不是升级 wasd_local

frida 17.x 需要 **Python 3.11+**，而 wasd_local 是 **3.10**。原地升级它意味着：

* conda 干跑会说「只需下载 28 MB」——**这是假的**，因为 conda 只管它自己装的包
* 真正的重家伙全是 pip 装的，且二进制扩展绑死在 cp310：

  ```
  torch/_C.cp310-win_amd64.pyd
  numpy/_core/_multiarray_umath.cp310-win_amd64.pyd
  ...  共 230 个 cp310 专属扩展
  ```

* Python 3.11 加载不了 cp310 的 .pyd，所以升级后要重装：

  | 包 | 体积 |
  |---|---|
  | torch | 4,416 MB |
  | cv2 | 112 MB |
  | scipy | 111 MB |
  | 其余 | 约 120 MB |
  | **合计** | **约 4.8 GB** |

* **降级不是免费的**：要再下一次同样的 4.8 GB。来回约 9.6 GB。

（技术上可行 —— torch 2.5.1 有 cp311 wheel，opencv 5.0.0.93 是 cp37-abi3 通用轮子。
只是性价比太低，而且动的是一个**已验证可用**的环境。）
